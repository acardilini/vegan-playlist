# Sub-project G — Junk-lyrics checker (design)

Date: 2026-10-13 · Status: spec, awaiting curator review · Branch: `session-junk-lyrics`

## 1. Purpose and agreed understanding

Some stored lyrics are not lyrics. The curator named two kinds, and the data confirms both:

- **Error stubs (185 songs).** A scraper wrote its failure message into `song_lyrics.lyrics`:
  "Error: Lyrics container not found on this Bandcamp page." (155), "Error: Scraper for this domain is not
  implemented." (26), "Error: Could not find lyrics container on the page." (4).
- **YouTube-description text (~32 candidates).** Mostly "Provided to YouTube by … ℗ …" boilerplate, plus a few channel
  blurbs with links. **Not all are pure junk:** one is a Genius page whose real verse follows a "N Contributors …
  Lyrics" header, and one is a blurb that also contains real lyrics. So description-type detection is
  *detect-and-confirm*, never auto-delete.

Today both kinds count as "has lyrics" (the check is only non-empty), so these songs never appear in **Needs lyrics**,
and **36 flagged songs already have an analysis** built from the junk, shown publicly.

**Success:** the curator can see every junk-lyrics song in one admin queue, dismiss false positives for good, clear real
junk so the song falls into Needs lyrics, and **no public page shows an analysis derived from flagged lyrics**.

**Curator decisions:** (1) while a song is flagged its analysis is **hidden publicly** (not merely listed); it returns when
the flag clears (Not junk, or real lyrics saved). (2) Detect-and-confirm for the description kind. Earlier note (2026-10-12):
the curator may also fix this in the separate analysis project; this feature does not depend on that.

**Out of scope (YAGNI):** auto-deleting any lyrics; writing to `song_lyric_analysis` (the web app stays a read-only
consumer); scheduling scans; a flag UI on the public site.

## 2. Detector — `backend/services/lyricsQuality.js` (new, pure, no DB)

`classify(text) -> 'error' | 'youtube_description' | null`. Exported `JUNK_KINDS = ['error','youtube_description']`.

- **error:** trimmed text starts with `Error:` (case-insensitive) and is short (< 200 chars).
- **youtube_description:** any of: contains "Provided to YouTube by" or "Auto-generated by YouTube"; **or** at least two
  distinct description markers (a URL, "subscribe", "follow us", "released on", "all rights reserved", a `℗` line,
  "download the song") **and** no verse structure evidence (bracketed `[Verse`/`[Chorus` headers, or many short lines) —
  tuned during implementation against the ~32 real candidates, with the borderline ones listed for the curator at smoke.
- Empty / whitespace-only → `null` (that is "no lyrics", already handled).
- Rules are conservative: a missed junk row costs nothing new; a false positive costs a temporary public analysis hide
  until the curator clicks **Not junk**.

## 3. State — migration 012 (additive, idempotent)

On `song_lyrics`:

- `junk_kind VARCHAR(30) NULL CHECK (junk_kind IS NULL OR junk_kind IN ('error','youtube_description'))`
- `junk_dismissed BOOLEAN NOT NULL DEFAULT FALSE`

**Flagged ⇔ `junk_kind IS NOT NULL`.** The flag lives on `song_lyrics` (not `songs`) because it describes that text and must
be reset when the text changes. (`song_lyrics` stays local-only; nothing here selects `lyrics` from a public route.)

## 4. Service — `backend/services/junkLyrics.js` (new)

- `scan(db)` — for every `song_lyrics` row with `junk_dismissed = false` and non-empty lyrics, set `junk_kind = classify(lyrics)`
  (including clearing a stale flag). Idempotent; writes only the two junk columns; returns `{ scanned, flagged, cleared }`.
- `listJunk(db, { limit, offset })` — flagged songs: `id, title, artists, status, published, junk_kind, snippet` (first ~120 chars,
  whitespace-collapsed), `has_analysis`. This is the **one** place lyric text is read for admin display and it truncates server-side;
  it is behind admin auth only.
- `dismiss(db, songId)` — `junk_kind = NULL, junk_dismissed = true`. 404 if no lyrics row.
- **Clearing** reuses the existing `curation.saveLyrics(…, { lyrics: '' })` path (blanks the text; keeps source URL/translation).
- `curation.saveLyrics` calls a small `junkLyrics.recheck(db, songId)` after saving non-empty text: resets `junk_dismissed = false`
  and sets `junk_kind = classify(text)`; after an empty save it sets `junk_kind = NULL`. So new scraper errors are caught as written
  through the workbench; rows written straight to the table by other tools are caught by **Scan**.

## 5. Public hiding — the shared analysis fragment (`services/analysis.js`)

- `LATEST_ANALYSIS` gains `WHERE NOT EXISTS (SELECT 1 FROM song_lyrics jl WHERE jl.song_id = song_lyric_analysis.song_id AND jl.junk_kind IS NOT NULL)`
  inside its `DISTINCT ON` subquery, so every join on it sees no row for a flagged song.
- `hasAnalysisExists(alias)` (a separate raw-table `EXISTS`) gets the same exclusion.
- **Inherited with no per-query edits:** song page, browse facets and counts, `/search` filters, `themeCounts`, Explore colour-by,
  the About reference counts and coverage, analytics, and the admin `needs-analysis` queue.
- **Contract kept:** the latest-pass-by-recency rule is unchanged; hiding is a pure exclusion, never a different pass.
- Lifts automatically when the flag clears.

## 6. Admin

- **Curation queues (`services/curation.js`):** `HAS_LYRICS_SQL` additionally requires the lyrics row's `junk_kind IS NULL`, so a
  flagged song reads as **no lyrics** — it appears in **Needs lyrics** (if included, unparked) and is never in **Needs analysis**
  (whose inline lyrics check is replaced by `HAS_LYRICS_SQL`). `getWorkbench` `has_lyrics`/`completeness.lyrics` follow suit; the
  workbench response also carries `junk_kind` so the Lyrics panel can say "These lyrics look like <an error message | a YouTube
  description> — Not junk / Clear lyrics".
- **New queue `junk-lyrics`** (all statuses with a flagged row), rail entry **Junk lyrics** under *Needs work*, Dashboard count via
  `queueCounts`. Rows show kind chip + snippet; per-row actions **Not junk** and **Clear lyrics**; a **Scan for junk lyrics** button
  at the top (shows `flagged N, cleared M`).
- Routes (authed, in `admin.js` under the curation domain): `POST /junk-lyrics/scan`, `GET /curation/queue?queue=junk-lyrics` (existing
  queue route, extended with `junk_kind` + `snippet` on those rows), `POST /workbench/:id/junk-dismiss`.

## 7. Risks

- **Shared fragment edit** is the one change to a public read path: covered by tests that a flagged song disappears from the song
  read, the browse facet count and `hasAnalysisExists`, and reappears on dismiss.
- **False positives** (real lyrics with a header) hide analysis until dismissed — mitigated by conservative rules, the confirm queue,
  and listing borderline cases at smoke.
- **Performance:** one extra `NOT EXISTS` per analysis join; `song_lyrics.song_id` is its primary key (indexed). Measure against the
  Explore points query and browse facets at smoke.
- Scan reads all lyric text into Node once (942 rows) — fine at this size.

## 8. Testing

- `lyricsQuality` unit tests: the three real error messages, "Provided to YouTube by …", a channel blurb with links, a Genius-header
  page with a verse (→ `null`), a short real lyric (→ `null`), empty (→ `null`).
- `junkLyrics` service tests (DB, own sentinel prefix `ZZZJUNK`): scan flags / clears / skips dismissed; dismiss; saveLyrics re-check
  (error text flags; real text clears and resets dismissal).
- Public-read tests: flagged song absent from `getSongAnalysis`, `hasAnalysisExists`, a browse facet count; present again after dismiss.
- Curation tests: flagged song in `needs-lyrics` and `junk-lyrics`, not in `needs-analysis`.
- Live check on one real flagged song (public page analysis gone, then Not junk → back), restored afterwards.
