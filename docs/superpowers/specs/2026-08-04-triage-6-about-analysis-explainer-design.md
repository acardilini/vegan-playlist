# Triage 6 — About: analysis explainer, AI disclosure, and editable page copy — design

**Date:** 2026-08-04 · **Branch:** `session-triage-6-about-analysis` (from `main` at `84e0841`)
**Source:** curator-triage backlog item 6 ([`CURATOR_TRIAGE_BACKLOG.md`](../../CURATOR_TRIAGE_BACKLOG.md),
"About / transparency"), plus a curator request made during this brainstorm to make the About copy
editable from a file.

## 1. Why this exists

Two things meet here.

**The site explains nothing about its own analysis.** Every song page shows thematic codes, seven
lyric-metadata judgements and six sound dimensions; the browse sidebar filters on all of them; the
Explore map places songs by embedding. Nowhere does the site say what any of it means or where it came
from. The definitional copy exists — the curator wrote it, and the API already serves it
(`scalarFacets`/`facetTree` `description`) — but the browse UI deliberately never shows it. That
omission is a **standing decision, not an oversight**: definitional copy belongs on an About page and
only usage help sits beside a control (`CLAUDE.md`, `ScalarFacetGroups`; curator rejected sidebar
definitions twice). This is the page that copy was being saved for.

**The site does not disclose its use of AI.** The per-song coding is model-generated by the curator's
separate analysis pipeline and read here read-only. A visitor has no way to know that, and the current
About page's "Our approach" section reads as though a person tagged each song by hand.

**And the About page's copy is locked in JSX.** The curator wants to write and revise it in a file
without editing a component.

## 2. What already exists, and the one thing that doesn't

| Source | Holds | Served today? |
|---|---|---|
| `taxonomy.json` `hierarchy` + term lists | 5 thematic dimensions, their sub-dimensions and groups, **141 terms** with definitions | dimension descriptions only |
| `master_metadata_codebook.json` via `metadataCodebook.js` | 7 lyric-metadata components, descriptions, per-code labels + definitions + inclusion rules | descriptions + in-use codes |
| `acoustic_codebook.json` via `acousticCodebook.js` | 6 sound dimensions, descriptions, **`derivation_source`**, per-code **`threshold`** | descriptions + in-use codes |
| `services/explore.js` | vector spaces, the two similarity metrics | as map/song-page data |

**`GET /api/analysis/facets` cannot serve a reference page, and this was verified in the code before
designing.** `analysis.facetTree` keeps only codes whose count is greater than zero
(`.filter(c => c.count > 0)`, `analysis.js:227`), then drops any group and any sub-dimension left
empty, and returns `{code, label, count}` with **no `definition`**. That is right for a filter sidebar, where an option matching nothing is noise, and
exactly wrong for a glossary, where a term no song currently carries still needs to be listed and
defined — the gap between the taxonomy's size and the coded corpus is itself information.

So the reference data needs its own endpoint. It does **not** need its own copy of the codebooks.

## 3. Decisions

Taken in this brainstorm. Each records the curator's call and the reason.

1. **Two pages, not one.** A narrative explainer and a reference glossary, rather than one page trying
   to be both. Each stays short enough to be read.
2. **Tabs under `/about`,** reusing the `ExplorePage` shell pattern. Nav keeps one "About" item; no new
   top-level section competing with Explore for the same mental slot.
3. **The reference lists everything, rendered from the API** — all 141 thematic terms including
   zero-count ones, all 7 components, all 6 sound dimensions. Rendering from the API rather than
   hand-writing the copy means the page can never drift from what the filters actually show.
4. **The four suppressed absence codes stay hidden** (`THEMATIC_ABSENCE`, `ABSENCE_OF_FOCUS`,
   `INSUFFICIENT_DATA`, `UNSPECIFIED`). They mark "the model found nothing", not a finding about a
   song, and the 2026-07-22 decision hid them from display and filters alike. The caveats section says
   "not every song is coded" in plainer words than a code named `INSUFFICIENT_DATA` would.
5. **One scroll with a sticky jump nav,** not sub-tabs inside the tab. Ctrl-F finds any term on the
   page and a deep link to one term always works.
6. **Counts, and each term links through to a filtered browse.** The glossary doubles as a second way
   into the catalogue, and a term showing `0 songs` is an honest coverage signal.
7. **Sound: method named, thresholds shown.** Each dimension states what was measured and each code its
   cut-off. These are the one genuinely reproducible part of the analysis; hiding the numbers would
   waste that.
8. **AI disclosure is method-level prose plus a dated "currently" line.** Durable text survives a model
   swap; the dated line is specific about today. **The dated line is computed, not typed** (§5.3) — a
   hand-typed model name goes stale silently, which is the failure mode the dating was meant to prevent.
9. **The codebooks are human work and the page says so first.** Curator's wording: the taxonomies were
   checked and iterated multiple times to develop a sensible set of codes — human-supported work. It is
   correct to say the **per-song coding is model-generated and currently unchecked**, and that human
   checking and coding may be future work. Both halves are stated; neither is softened.
10. **Page copy lives in editable Markdown files** in `backend/data/`, served by the API so an edit is
    live on refresh, **with the last-committed copy bundled as a fallback** so the page cannot break if
    the API is down.
11. **`react-markdown` is added as a dependency.** The project's habit is to avoid libraries (the
    Explore scatter is hand-rolled), but that habit was applied to a charting library — large, and the
    hand-rolled replacement is ~200 lines of drawing fully under our control. A Markdown parser is a
    different kind of problem: correctness-critical, thoroughly solved, and a hand-rolled subset fails
    by *silently* rendering a construct as literal text, which is the worst possible failure for a file
    the curator writes prose into.
12. **Live numbers reach the prose as `{{tokens}}`,** so the curator controls the sentence around a
    figure. An unrecognised token renders as itself, making a typo visible rather than silent.

## 4. Architecture

### 4.1 Routing

`AboutPage.jsx` becomes a tab shell (a near-copy of `ExplorePage.jsx`: `NavLink` × 3 + `Outlet`).
Today's About content moves out into its own component. Three real routes, all linkable:

| Route | Tab label | Component |
|---|---|---|
| `/about` | About | `pages/about/AboutOverview.jsx` |
| `/about/analysis` | How the analysis works | `pages/about/AnalysisExplainer.jsx` |
| `/about/reference` | Reference | `pages/about/AnalysisReference.jsx` |

`/about` keeps working exactly as it does today, so no redirect is needed and no existing link breaks.

### 4.2 The content pipeline (About + explainer)

```
backend/data/about.md      ─┬─> GET /api/content/about     ─┐
backend/data/analysis.md   ─┘    GET /api/content/analysis  │
        │                                                   ├─> <MarkdownPage>
        └── Vite ?raw import at build time (fallback) ──────┘        │
                                                                     ├─ substitute {{tokens}}
                                                                     └─ react-markdown
```

**Serving.** `GET /api/content/:slug` in a new `backend/routes/content.js`, mounted at `/api/content`.
`slug` is checked against a hard-coded whitelist `{about, analysis}` and mapped to a filename — the
request string never reaches a path join, so traversal is impossible by construction rather than by
sanitising. Returns `{ slug, markdown }`; 404 for an unknown slug; 500 with a logged error if the file
is unreadable.

**Fallback.** The same two files are imported at build time with Vite's `?raw` directly from
`backend/data/`, so there is **one file in git, not two** — a copied fallback would drift the first time
someone edited only one of them. `<MarkdownPage>` renders the fetched copy when the fetch succeeds and
the bundled copy when it fails, with no error UI: a visitor should never see the site's own plumbing.

> **Verified 2026-08-04, before this spec was written.** A `?raw` import of
> `../../backend/data/acoustic_codebook.json` was added to the frontend as a temporary probe.
> `npm run build` succeeded (107 modules transformed), and under `vite dev` the module resolved to a
> `/@fs/…` URL that served **200** with the file's contents. **No `vite.config.js` change is needed** —
> Vite's default `server.fs.allow` already resolves to the repo root above `frontend/`. The probe and
> its `main.jsx` import were reverted; the tree was confirmed clean afterwards. The `prebuild`-copy
> alternative considered during the brainstorm is therefore **not** needed and is not part of this
> design.

### 4.3 The reference pipeline

```
taxonomy.json          ─┐
metadataCodebook.js    ─┼─> services/referenceCodebook.js ─> GET /api/analysis/codebook ─> AnalysisReference
acousticCodebook.js    ─┘              │
                                       └─ counts: one query per family, LATEST_ANALYSIS +
                                          status='included' AND published=true
```

`services/referenceCodebook.js` **composes the existing owners; it does not re-read their files.**
`metadataCodebook.js` and `acousticCodebook.js` stay the single owners of their JSON, which is what
keeps label rules and suppression in one place. Two small additive getters are needed on
`acousticCodebook.js`, since it exposes neither field today:

- `derivationSource(key)` → the dimension's `derivation_source` string
- `codeThreshold(key, code)` → that code's `threshold` string

Both follow the existing `componentDescription` / `codeDefinition` shape and return `''` when absent.

Counts are three queries — thematic, scalar, acoustic — each reusing the shared `LATEST_ANALYSIS`
fragment and the `status='included' AND published=true` publish gate, exactly as every other public
read does. Terms with no songs are kept, at count 0.

### 5.3 The token set

`frontend/src/utils/contentTokens.js` — pure, no DOM, no React, node-testable like
`exploreUrlState.js`. `substituteTokens(markdown, values)` replaces `{{name}}` where `name` is known and
leaves the literal `{{name}}` in place where it is not.

| Token | Renders | Source |
|---|---|---|
| `{{songs}}` | `1,333` | `coverage.live_songs` |
| `{{artists}}` | `635` | `coverage.artists` |
| `{{analysed}}` | `693` | `coverage.analysed_songs` |
| `{{analysedPct}}` | `52%` | derived |
| `{{mapped}}` | `640` | `coverage.mapped_songs` |
| `{{codingModels}}` | `gemini-3.5-flash-lite` | `latest_pass_models`, names only, count-desc |
| `{{codingDate}}` | `July 2026` | `latest_pass_at`, month + year |

`{{codingModels}}` lists **every** model in the latest-pass set, ordered by song count. Today that is
two names, one of which covers a single song. Listing it is the honest output; the curator's prose can
frame it however reads best, which is the point of putting it in a file they own.

The About tab needs `{{songs}}` and `{{artists}}` only, so `AboutOverview` keeps fetching
`/api/spotify/stats` exactly as it does today. The explainer needs the coverage figures, which ride
along on `/api/analysis/codebook` rather than justifying a third endpoint — it is one small block on a
response the Reference tab already fetches.

## 6. The two Markdown files

Both ship with a **complete first draft** so the curator edits prose rather than facing a blank file.
The drafts are mine; the voice is theirs to replace.

### 6.1 `about.md`

Today's five sections carried over verbatim as Markdown — mission, what we include, our approach, get
involved — with the two stat figures becoming `{{songs}}` and `{{artists}}`. **Nothing a visitor sees
changes on day one.** "Our approach" gains a link across to the explainer, since that is now where the
real answer lives. The three stat badges stay as JSX below the rendered Markdown: they are layout, not
prose, and pulling them into Markdown would mean inventing a widget syntax.

### 6.2 `analysis.md`

Eight sections, in this order. The order matters: the human work is stated before the machine work,
because it is what makes the machine work mean anything.

1. **What gets analysed** — a song's lyrics, its recording, and its position relative to every other
   song.
2. **The codebooks are human work** — the taxonomy and codebooks were designed, tested and revised over
   multiple rounds to arrive at a set of codes that actually describes this music. This is the part
   with a person's judgement in it.
3. **Reading the lyrics** — a large language model reads each song and applies that codebook. Each song
   shows its **latest** pass; a re-run can change what a song carries.
4. **Measuring the sound** — six dimensions computed from the audio by signal analysis, not opinion.
   Names the method; links to the Reference for the thresholds.
5. **Placing songs in space** — embeddings and the projections behind the Explore map; the two "You
   might also like" tabs measure different things (words vs sound).
6. **Where the rest comes from** — genre and album data from Spotify; mood (`songs.custom_mood`),
   language and lyric highlights entered by the curator. **Open question for the curator to settle when
   editing this section:** this reads `custom_mood` as curator-entered and genres as Spotify-derived
   via `EFFECTIVE_GENRE_EXPR`; confirm before publishing.
7. **AI use, plainly** — which steps are model-generated, which are measured, which are human. Durable
   method-level prose, then one line: "As of `{{codingDate}}`, each song's most recent coding pass came
   from `{{codingModels}}`."
8. **What this doesn't tell you** — `{{analysed}}` of `{{songs}}` songs have a coding pass
   (`{{analysedPct}}`), `{{mapped}}` appear on the map; the per-song coding is machine-applied and
   **currently unchecked**, with human checking and coding as possible future work; the codes describe
   what a song *says*, not whether it is any good.

## 8. The Reference page

One scroll. A sticky jump bar (`Themes · Lyric metadata · Sound`). Every dimension is a
`FilterSection` — the same primitive the browse sidebar uses, so a group opens and closes identically in
both places, and the nesting that already carries five theme dimensions and seven metadata components
carries them here too. Dimensions render collapsed; a URL fragment (`/about/reference#targets`) opens
and scrolls to its dimension.

Each term renders as label · definition · count, with the count linking to
`/?<dim>=<code>`. **No new URL plumbing is required:** `readFilterState` already parses `themes`,
`targets`, `actions`, `tactics`, `moral_frames`, the seven scalar keys and the five acoustic keys as
array params. A small `termHref(dimension, code)` helper builds the string. A term with count 0 renders
its count as plain text, not a link — a link to an empty result set is a dead end.

Sound dimensions additionally render their `derivation_source` under the heading and each code's
`threshold` in a muted monospace line beneath its definition.

## 9. Testing

**Backend (`node:test`, existing runner).** Per the per-file sentinel convention, any fixture rows use a
prefix unique to these files.

- `referenceCodebook`: every taxonomy term appears including zero-count ones; the four suppressed codes
  are absent; a term's count matches a direct query for that code; `derivation_source` and `threshold`
  are populated for every acoustic code; the shape matches §5.2.
- Content route: each whitelisted slug returns its file; an unknown slug 404s; a traversal-shaped slug
  (`../../.env`) 404s rather than reading anything.
- Publish gate: an unpublished song's codes do not raise any count. This is the invariant that the
  retired `vector_space.json` violated, so it is tested rather than assumed.

**Frontend (`node --test`, as `exploreUrlState.js` uses).**

- `contentTokens`: every token substitutes; an unknown token passes through literally; a token inside a
  code fence is left alone; number formatting is locale-grouped.
- `termHref`: builds a param the existing `readFilterState` parses back to the same selection.

**Puppeteer smoke.** All three tabs render and are linkable; `/about` is unchanged from today; a term's
count click lands on a browse filtered to that code with results; the Reference page lists a known
zero-count term; the explainer's coverage sentence shows real numbers, not raw `{{tokens}}`; and — with
the backend stopped — both Markdown pages still render from the bundled fallback.

## 10. Out of scope

- **No editing UI.** The curator edits the `.md` files directly; no admin surface for page copy. (YAGNI.)
- **No new taxonomy content.** Every definition on the Reference page comes from files that already
  exist; this session writes none of them.
- **Nothing is written to any analysis table.** Read-only throughout, like `services/explore.js`.
- **The Year-range control's two carried bugs stay carried.** Real, cheap, and unrelated to this page.
- **No site-wide CSS sweep.** Only `.about-container` and `.page-container` are checked for the
  `margin: 0 auto` no-stretch bug Batch B found (Watch-outs, 2026-08-04), because this session opens
  those pages. The rest of the sweep stays where it is.

## 11. Watch-outs

- **`react-markdown` is the first new frontend dependency in a long while.** It must be added with
  `remark-gfm` only — no raw-HTML plugin. `react-markdown` escapes HTML by default and that default is
  load-bearing here, since the Markdown arrives over HTTP from a file on disk.
- **The bundled fallback is a build-time snapshot.** After the curator edits a `.md` file, the fallback
  is stale until the next build. That is correct behaviour — the fallback exists for an unreachable
  API, not for freshness — but it should be said plainly in the implementation notes so nobody
  "fixes" it later.
- **The counts query must not become a fourth latest-analysis join pattern.** It reuses
  `LATEST_ANALYSIS`; if it starts drifting, the reference page will disagree with the browse sidebar,
  which is the exact failure this design exists to prevent.
